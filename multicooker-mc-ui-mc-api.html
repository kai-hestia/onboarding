0速览：两个仓库是什么

MC（Multicooker，多锅炒菜机）这一台机器上的"前端 + 后端"两件套。

mc-ui multicooker-ui

跑在机器触摸屏上的 Vue 3 应用（800×1280 竖屏）。点菜、做菜流程、主厨模式、清洁、设置、App Library 都在这里。

npm run dev → :3001；npm run build → ui/ → ui.zip → 上传 Azure Blob。

mc-api multicooker-api / multicooker-data

机器上的 Node.js (Express) 本地服务，:3000。持有机器状态、串口协议、MQTT、菜单文件、设置、升级逻辑，并托管 mc-ui 的构建产物。

systemd 服务 multicooker.service，WorkingDirectory /multicooker，node ./index.js。

一句话关系 mc-api 是"机器的操作系统接口"，mc-ui 是"机器的脸"。浏览器加载的是 mc-api 静态托管的 mc-ui 页面，页面再通过 HTTP + WebSocket 跟 mc-api 交互。

2.2 状态驱动的路由（重点，改页面前必读）

mc-ui 的页面不是用户想去哪就去哪——机器状态会强制导航。链路是：

  1. main.js 连 WebSocket ws://<ip>:3000/machine/status，把每帧 JSON 覆盖进 MachineStatus store（同时维护 MachineStatusPrev）；断线 1s 后自动重连。
  2. 每帧都会调用 protocol.js 的 route_machine_status(global)，按状态跳转（见下表）。
条件跳转 / 行为
server_state === 'SLEEP'强制 /sleep
server_state === 'FAILURE'强制 /error（10s 收不到控制板 ~STATUS 就会进入）
system_state === 'ERROR'/error?error_name=…（按错误码映射 overheat / gripper / emo…）
system_state === 'RESET'/qrcode（激活页；在 /init 或 route_exclude 时不跳）
system_state === 'PRECOOK'cook 阶段 1 → /cook/prepare；阶段 2 → /cook/cooking
system_state === 'COOK'/cook/cooking
system_state === 'IDLE'仅当当前在 /cook* 时回 /home（从启动页 / 不会自动进首页）
alert_id !== -1按 alert_id_to_popup_name 弹窗；-1 = 无报警

例外名单 route_exclude：/backend、/settings/general、/settings/factorysettings 不会被强制跳走。

无硬件 / 本地调试时的三个连锁反应 ① 没有 ~STATUS → 10s 后 FAILURE，页面被拉到 /error；
② 启动页 / 不会自己前进，必须靠 RESET → /qrcode → 激活(INIT) → /init → /home 这条链路，本地模拟器因此开机就发 RESET；
③ 想自由跳页面：把 settings.mjs 的 disable_route_status 打开（App.vue 里按 Enter 也会开，但同时会把 API IP 切回固定地址，谨慎用）。

3.2 Machine：串口与状态广播

  • MachineStatus 是一个巨大的构造函数对象：version、server_state、system_state、online、alert_id、wok 温度、heating、cook（id/order_number/阶段/剩余时间/box_status）、io、motor、motion_state、settings… UI 那一堆 MachineStatus?.xxx 都来自它。
  • 串口命令 serial_cmd(line)：拆词 → COOK 特殊处理（初始化烹饪状态、解析订单号）→ 普通命令加帧长填充 + PC 版 CRC16 → 压入 100Hz 的 serial_buffer 由 10ms 定时器发送。文件下发则分块走同一 buffer。
  • 状态广播：ws_send_machine_status() 把整个 MachineStatus 逐客户端 send；每 1s 检查控制板存活，10s 无响应 → FAILURE / Controller Status Timeout。
  • 客户端数 /machine/clients + UI.start_chromium_check()：一个浏览器都不连就重启服务（防止白屏）。

3.4 控制板协议（串口帧与 ~ 响应）

mc-api 与控制板（PIC32）跑一条"下行定长帧 + 上行文本行"的协议，串口是 /dev/ttyS9，桥接程序是 bin/serialcom。看懂它，就知道本地模拟器在演什么。

下行：命令帧（mc-api → 控制板）

// 普通命令：定长 52B
"COOK 1\n"  → NUL 填充到 50B  → 2B CRC16

文件下发另走分块：每块 ≤1024B + 2B CRC，由 100Hz 的 serial_buffer 排队发送。

上行：~ 文本行（控制板 → mc-api）

~STATUS: {"status":"IDLE","sys":"IDLE",
  "alert":-1,"temperature":25,"cook":0,...}
~CMD: OK
~ORDER: 12
~PREPINFO: 0 1 1 1 1 1 1 1 0
~COOKINFO: 0 (POURBOXF) (WOKTEMP 180) 1 3 60 180
~INIT: 127 127
响应作用 / 对应代码
~STATUS: {json}1Hz 心跳 + 状态源。parse_status() 只取：status（IDLE/BUSY → online）、sys（→ system_state）、alert（→ alert_id，-1 = 无报警）、temperature/target/heating、cook（0 空闲 / 1~3 阶段）、motion（运动位图）。10s 没有 → FAILURE。
~CMD: OK / RESEND / ABORT普通命令的完成 / 要求重发 / 中止应答，用于清 cmd_in_progress。
~UPLOADF: START / CHUNK / RESEND / ABORT文件上传握手：START 开始、每收一块回 CHUNK、块发完即结束。
~ORDER: <id>写 MachineStatus.cook.id，UI 用它对齐选中的菜谱。
~PREPINFO: mode b1…b7 taken备菜模式 + 7 个料盒状态。
~COOKINFO: mode (cur) (next) step total remain totalSec烹饪进度：当前/下一步动作、第几步、剩余秒（烹饪页圆环与"下一步操作"）。
~INIT: flag mask自检位图；(flag & mask) === mask 时 Init.vue 跳 /home。
~DEADBEEF控制板重启握手；非首次出现 → FAILURE / Controller Unexpectedly Restarted。
做菜时其实发生了两次"下发" COOK <recipeId> 先在 menu/machine/ 找对应菜谱（文件名形如 1_1_v1.json，须含 id/version/uuid），复制成 tmp/recipe.json，走 UPLOADF 分块上传并逐块等应答；文件传完才把 COOK 命令真的发给控制板。

3.5 运行时全链路（启动 / 做菜 / 睡眠 / 重启）

把 §2.2 的跳转规则和 §3.4 的协议连起来，就是机器的四条主干流程；本地模拟器就是照这四条演的。

① 开机 → 激活 → 首页

开机systemd 拉起 mc-api
→
控制板 RESET~STATUS sys=RESET
→
UI /qrcode激活页
▼ 点"激活" → send_cmd('INIT') → ~INIT: 127 127 → Init.vue 轮询到完成
UI /init → /home7 项自检全绿

注：require('./src/Serial') 时就会 start_serial()（board_disable/enable → spawn serialcom），所以 API 一起来串口就开始工作。

② 做菜（菜单 → 烹饪）

/menu → /menu/recipes选菜谱
→
COOK <id>/machine/cmd?cmd=COOK…
→
UPLOADF → ~ORDER上传菜谱 + 设置 id
▼ PRECOOK 1 → 2 → COOK；UI 依次在 /cook/prepare、/cook/cooking（~COOKINFO 每秒更新）
回 /homesys=IDLE 且当前在 /cook*

③ 睡眠 / 唤醒

  • 睡眠：GET /machine/sleep → server_state=SLEEP、亮度 20、board_disable.sh → UI 强制 /sleep。
  • 唤醒：GET /machine/wake → 亮度 100、board_enable.sh、重建 MachineStatus → UI 恢复；按钮同时 push('/')。

④ 重启

  • GET /machine/restart → service_restart.sh → systemctl restart multicooker：API 进程被 systemd 重启，浏览器端 WS 断线 1s 后重连。
  • UI 侧 global.restart() 还会 push('/start') —— 这条路由不存在（只有 /），会落在空白页；详见 §8。

为什么不是 npm start

v6 HEAD 的 src/Menu.js 顶部用 require()、底部却 export，任何 Node 版本都无法直接运行（新 Node 会当 ESM 加载，然后在 require 处报错）。ncc/webpack 能容忍这种混用，所以本地跟产线一样跑 bundle。

这也是上游 bug，值得单独修。

机器上的运行形态

systemd multicooker.service：WorkingDirectory=/multicooker，ExecStart=node ./index.js；ui_start.sh 拉起 Chromium 全屏。

UI.js 每 15s 检查有没有浏览器连着（没有就重启服务）；每 30s 检查触摸屏。

为什么不用 larder 那套脚本

同事给的 get_devtools_url.ps1 / 1_build_bak_upload.ps1 是 larder 的流程：orangepi 用户、ldapi.service、dist/、停 lightdm、DevTools 33012。

在 mc6 上这些前提都不成立：scp/rsync 写不进 /multicooker/ui，mc 不能直接 systemctl restart，kiosk 也没开 DevTools 端口。它们只适合当参考。

6.1 推荐方式：设备自带的 HTTP 更新接口

POST /update/upload 本来就是 /update/updater 网页和 Azure 升级共用的入口。直接 POST 一个 ui.zip 给它，就等价于“本地上传升级包”：mc-api 以 root 身份删掉旧的 /multicooker/ui、解压新包并重启 multicooker.service，kiosk Chromium 随之重启并加载新页面。下面这套流程已封装成 uv shebang 脚本 ~/repos/onboarding/update-mc-ui-at-mc6，可直接运行。

mc-ui 构建npm run build → tmp/ui.zip
→
curl 上传POST :3000/update/upload（字段 ui）
→
root 替换 + 重启multicooker.service
→
kiosk 刷新startx + Chromium
# ---------- 一次性：SSH 配置（~/.ssh/config） ----------
Host mc
    HostName 10.31.1.101
    User mc
    IdentityFile ~/.ssh/id_mc
    IdentitiesOnly yes

# ---------- 构建 + 校验 ----------
cd ~/repos/mc-ui
# 构建前确认 settings.mjs 里 custom_server_origin / disable_route_status 都是 false
npm run build                       # vite build → ui/；zip_files.js → tmp/ui.zip
unzip -t tmp/ui.zip                 # 完整性检查
unzip -l tmp/ui.zip | grep -q 'ui/index.html' || echo '!! zip 结构不对，别上传'   # 顶层必须是 ui/

# ---------- 备份当前部署（只读拉取，不需要 sudo） ----------
ts=$(date +%Y%m%d-%H%M%S); mkdir -p backups
rsync -a mc:/multicooker/ui/ backups/ui-$ts/                # 实际部署内容（主机名用别名 mc:，不要写 IP）
scp mc:/multicooker/tmp/ui.zip backups/ui-$ts.zip           # 设备上最近一次升级包

# ---------- 上传（字段名必须是 ui；千万不要带 api / firmware） ----------
curl -f -F "ui=@tmp/ui.zip" http://10.31.1.101:3000/update/upload
# 响应先于重启发出，curl 可能报 connection reset / 空响应；成功与否以下面的校验为准

# ---------- 校验 ----------
curl -s http://10.31.1.101:3000/ | grep -o 'assets/index-[^"]*\.js'   # 与本地 ui/index.html 对比
ssh mc 'systemctl is-active multicooker'                              # 期望 active
curl -s http://10.31.1.101:3000/machine/clients                       # kiosk 的 WS 客户端应重新出现
为什么不能用 scp / rsync 直接覆盖 /multicooker/ui 属于 root，mc 既没有写权限也没有免密 sudo；而 POST /update/upload 由 root 的 mc-api 处理，相当于借设备自己的手完成替换。rsync 在 mc6 上只能用来从设备往回拉做备份。另外 rsync/scp 的主机名必须写成 ssh 别名 mc:；写成 mc@10.31.1.101 会匹配不到 ssh config 里的 Host mc，退化成密码认证。

6.3 坑与注意

  • 更新是“先删后解压”，而且失败会被吞掉：update_ui() 先 rm -rf ui 再 unzip；unzip 失败只写日志，/update/upload 仍返回成功。坏包 = 白屏且没有自动回滚 —— 所以上传前必须校验 zip、必须备份。
  • HTTP 200 不代表部署成功：响应在重启前就发出了，随后进程会被 systemd 杀掉；Exec 还有 5s 超时（ui_start.sh 自己 sleep 5+1，容易踩线）。判断标准是页面资产 hash、systemctl is-active、/machine/clients。
  • 接口无鉴权：/update/upload 也接受 api 和 firmware 字段（后者会烧控制板固件）。只发 ui；端口 3000 不要暴露到实验室网络之外。
  • 版本号有两套：settings.version（构建时写死、UI 自己显示）和 Azure blob metadata（/update/version 读的“可升级版本”）。直连上传不会改 Azure；SoftwareUpdate 只在“远端 > 本地”时提示升级，所以本地升版本号是安全的，但别和以后要发到 Azure 测试通道的版本号撞车。
  • api.zip 会覆盖 bin/：Azure 升级 api 后 bin/ui_start.sh 回到仓库版本，任何调试改动（比如 DevTools 端口）都会丢；UI-only 上传会保留（chmod_x_api() 每次上传后都会把 bin/* chown 给 mc）。
  • 不需要清 Chromium 缓存：Vite 产物是带 hash 的文件名，index.html 每次重新校验，kiosk 重启后自然加载新资源。
  • UI 单独升级要和 API 对得上：mc6 上 API 是 v6 @ 6.0.8.0；如果 UI 分支依赖新接口，得先把对应的 api.zip 也升上去。

6.4 远程调试（DevTools）

mc6 的 Chromium 默认没开远程调试端口（ui_start.sh 里没有 --remote-debugging-port），所以同事的 get_devtools_url.ps1 在这里会拿不到 json/list。开启方式是改 bin/ui_start.sh（mc 有写权限），再调 /machine/restart 应用（同样不需要 sudo）：

# 一次性：给 startx 的 Chromium 参数加端口
ssh mc "sed -i 's/--disable-pinch/--disable-pinch --remote-debugging-port=33012/' /multicooker/bin/ui_start.sh"
curl -s http://10.31.1.101:3000/machine/restart

# 推荐：本地端口转发（默认只监听 127.0.0.1，比直接 --remote-debugging-address=0.0.0.0 安全）
ssh -N -L 33012:localhost:33012 mc
curl -s http://127.0.0.1:33012/json/list | head
怎么用 json/list 每条的 devtoolsFrontendUrl 就是调试页面路径；把其中的 host:port 换成 127.0.0.1:33012 后浏览器打开即可。列表里可能有多个 target，挑 url 为 http://localhost:3000/ 的那条，不要盲取第一条。
